# 1.0 Benchmark, Autonomous Review & IDE Integration Roadmap

> Umbrella roadmap for the 1.0 release, covering benchmark evidence, adversarial evaluation, autonomous repair, multilingual knowledge graphs, and JEditor/PyBreeze integration.

## Overview

This roadmap consolidates the major work required to move the project toward a reproducible, evidence-backed 1.0 release.

The current project already provides building blocks for benchmarking, adversarial evaluation, PR summarization, issue autofix, knowledge-graph grounding, pluggable inference backends, verification, telemetry, and reproducible run manifests.

The goal of this roadmap is therefore to **turn the existing capabilities into a complete, measurable, production-quality 1.0 workflow** rather than treating every item as an independent greenfield implementation.

## Workstreams

### W1. Full Public-Dataset Benchmark

Run a complete benchmark against a frozen public dataset and publish reproducible results.

#### Requirements (W1)

* Freeze dataset versions/revisions used for the benchmark.
* Run the complete public benchmark rather than a sampled subset.
* Record:

  * dataset revision
  * model/backend
  * configuration
  * random seeds
  * environment information
  * runtime
  * token usage
  * cost where available
  * failures and unsupported cases
* Produce deterministic aggregate metrics.
* Preserve raw benchmark artifacts.
* Publish machine-readable benchmark results.
* Document the exact reproduction command.
* Do not publish placeholder or estimated numbers.

#### Acceptance Criteria (W1)

* [ ] Full public dataset has been evaluated.
* [ ] Dataset revision is recorded.
* [ ] Run configuration is reproducible.
* [ ] Raw evidence is archived.
* [ ] Aggregate metrics can be regenerated.
* [ ] Failures and unsupported cases are reported separately.
* [ ] Benchmark results are documented publicly.

### W5. Make `pr-summary` an Independent Subcommand

Make Copilot-style PR summarization independently usable without requiring the complete review pipeline.

#### CLI

Provide an explicit command such as:

```text

```

#### Requirements (W5)

* Accept repository/PR input independently.
* Support normal text output.
* Support machine-readable JSON output.
* Allow backend/model selection.
* Support GitHub/GitLab/Gitea posting where supported.
* Support comment upsert/update.
* Make the operation idempotent.
* Avoid requiring expensive review/autofix stages.
* Preserve reproducible configuration in run metadata.

#### Acceptance Criteria (W5)

* [ ] `prthinker pr-summary` works independently.
* [ ] JSON output is available.
* [ ] Backend selection works.
* [ ] Summary can be posted as a PR comment.
* [ ] Existing summary comments can be updated.
* [ ] Re-running does not create duplicate comments.
* [ ] The command does not depend on the full review/autofix pipeline.

### W6. 17-Item Ablation Study

Perform a controlled ablation study covering the 17 mechanisms/components being evaluated by the project.

#### Experimental Design

Use:

* One fixed control configuration.
* 17 treatment configurations.
* Fixed model/backend for the primary experiment.
* Fixed dataset/corpus.
* Fixed evaluation protocol.
* Fixed random seeds where practical.

Each treatment should isolate one mechanism while keeping the remaining configuration unchanged.

#### Metrics (W6)

Collect:

* Review quality
* Issue coverage
* Precision
* Recall where ground truth exists
* Runtime
* Token consumption
* Estimated cost
* Failure rate
* Safety/security metrics where applicable

#### Statistical Analysis

* Use paired comparisons where the experimental design permits.
* Report confidence intervals.
* Report effect sizes.
* Apply appropriate multiple-comparison correction.
* Preserve per-case results rather than publishing only aggregate scores.

#### Acceptance Criteria (W6)

* [ ] All 17 ablations are defined.
* [ ] Control configuration is fixed.
* [ ] Experimental protocol is documented.
* [ ] Results are reproducible.
* [ ] Per-case data is archived.
* [ ] Statistical analysis is included.
* [ ] Aggregate results and limitations are published.

### W8. Make `issue-autofix` a Complete Autonomous Repair Loop

Turn issue autofix into a bounded autonomous software-repair workflow.

#### Target Flow

```text
Issue
  ↓
Fingerprint / Deduplication
  ↓
Issue Classification
  ↓
Repository Localization
  ↓
Patch Planning
  ↓
Minimal Patch Generation
  ↓
Isolated Worktree
  ↓
Static Verification
  ↓
Tests
  ↓
Post-Fix Review
  ↓
 ┌───────────────┐
 │ Passed?       │
 └───────┬───────┘
         │
    yes  │  no
         │
         ↓
   Draft Fix PR    Bounded Retry
```

#### Requirements (W8)

* Issue ingestion.
* Issue fingerprinting and deduplication.
* Relevant-code localization.
* Patch planning.
* Minimal patch generation.
* Isolated worktree execution.
* Static verification.
* Test execution.
* Post-fix review.
* Bounded retry.
* Explicit terminal states.
* Draft PR generation.
* Full audit trail.

#### Safety Requirements

The autonomous loop must have:

* Maximum retry count.
* Maximum execution time.
* Resource limits.
* Sandboxed execution where appropriate.
* Secret redaction.
* No uncontrolled external side effects.
* Clear failure states.
* Complete action/event logging.
* Human review before merging.

#### Acceptance Criteria (W8)

* [ ] Issue can enter the repair pipeline.
* [ ] Candidate patch is generated automatically.
* [ ] Verification runs automatically.
* [ ] Tests run automatically.
* [ ] Failed repairs can retry within configured bounds.
* [ ] Successful repairs produce a draft fix PR.
* [ ] All actions are auditable.
* [ ] Unsafe/unverified patches cannot be silently marked successful.

### W9. Online Review-Quality Evaluation

Measure review quality from actual usage rather than offline benchmark results alone.

#### Signals

Collect privacy-safe metrics for:

* Accepted findings
* Dismissed findings
* Applied suggestions
* Converted issues
* Reopened findings
* Regression findings
* Review latency
* Token usage
* Cost
* Model/backend
* Repository/project characteristics
* Quality drift over time

#### Evaluation Dimensions

Separate:

1. Objective issue matching where ground truth exists.
2. Model-based judging.
3. Human ratings.
4. User interaction signals.

Avoid treating any single signal as the complete definition of review quality.

#### Requirements (W9)

* Version evaluation schemas.
* Preserve anonymized/aggregated metrics.
* Track model/configuration changes.
* Detect quality drift.
* Support longitudinal analysis.
* Respect repository/user privacy.

* [ ] Online evaluation events are defined.
* [ ] Metrics can be aggregated by release/model/configuration.

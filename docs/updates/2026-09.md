## U-20260924-01 · 2026-09-24 · Workflows: no file names in shell, per-job permissions, pinned actions · #ci #security

- **What**: a scan with zizmor 1.30.1 (`zizmor --offline .github/workflows examples/prthinker.downstream.yml`) found shell injection, over-broad permissions, leftover credentials and movable action tags. All fixed in the four workflows and in the downstream example users copy:
  - **Shell injection from file names.** The review shard's preflight ran `echo "::warning::PRThinker skipped ${{ matrix.file }} — …"`. `matrix.file` is a path from the pull request, and `${{ }}` is pasted into the script before the shell runs it, so a file named `$(…)` would execute on the runner. The echo now reads `$PRTHINKER_TARGET_FILE`, which the step already sets from `matrix.file`. `kg-refresh.yml` passes `github.ref_name` through `env` the same way; it only runs on pushes to `main`, so there it is hygiene.
  - **Least privilege.** `prthinker.yml` gave every job `pull-requests: write` and `checks: write`. The workflow default is now read-only (`contents`, `pull-requests`, `checks`, `actions`), which is all the review shards use. `enumerate` raises `pull-requests: write` for the placeholder and PR summary. `aggregate` raises `pull-requests: write`, `checks: write` and `security-events: write`. The SARIF upload step (`upload-sarif`) needs `security-events: write`, which the workflow never granted; the step is `continue-on-error` and every recent run skipped it for lack of a report, so the gap had not shown.
  - **Credentials.** Every checkout except the `kg-refresh.yml` job that pushes the refreshed artifacts sets `persist-credentials: false`.
  - **Pinned actions.** All 31 references (17 in the example) name a commit with the version as a comment: checkout v7.0.1, setup-python v7.0.0, upload-artifact v7.0.1, download-artifact v8.0.1, cache/restore and cache/save v6.1.0, dependency-review-action v5.0.0, attest-build-provenance v4.2.2, codeql-action/upload-sarif v4.38.1 (the example was still on v3), gh-action-pypi-publish v1.14.2. ## U-20260925-01 · 2026-09-25 · Dependabot waits 7 days before proposing a new release · #ci #security #deps

- **What**: `.github/dependabot.yml` sets `cooldown: default-days: 7` on all 3 update blocks. Dependabot now proposes a version only after it has been public for 7 days, so a compromised release is more likely to be found and yanked before a PR exists. Without the setting Dependabot waits 3 days (its default since 2026-07-14). Security updates ignore the cooldown and still open at once. `github-actions` accepts only `default-days`, so no per-semver values are set.
- **Why now**: zizmor 1.30.1 (`zizmor --offline .github`) reported `dependabot-cooldown` (medium) on every block; the workflow scan earlier this week only covered `.github/workflows`.
- **Tests**: `tests/test_workflow_actions.py` checks that every update block waits at least 7 days. The previous config fails it.
- **Result / numbers**: zizmor medium findings 0. The workflow-actions test file passes.
- **Sources**: https://docs.zizmor.sh/audits/#dependabot-cooldown ; https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference#cooldown- ; https://github.blog/changelog/2026-07-14-dependabot-version-updates-introduce-default-package-cooldown/
